# Lecture notes

## 1. The evolution of NLP

| Approach | Representation | Context | Main limitation |
|---|---|---|---|
| Rules, statistics, n-gram LMs (1990s–2000s) | Words as symbols | n − 1 words | Sparsity; no similarity between words |
| Word embeddings (word2vec 2013, GloVe) | One dense vector per word | None at use time | One vector for all senses ("bank") |
| RNN/LSTM seq2seq (2014), + attention (2015) | Contextual hidden states | Whole sequence in theory | Sequential; long-range information fades |
| Transformer (2017) → BERT/GPT (2018) → GPT-3 (2020) → ChatGPT (2022) | Contextual vectors via attention | Thousands to millions of tokens | Cost with context; hallucination; data hunger |

An **n-gram model** predicts the next word using counts of the previous n − 1 words. A trigram uses two previous words. Long phrases often have no counts: **sparsity**. Counts also fail to share information between similar words such as cat and dog.

Neural language models introduced learned word vectors (Bengio et al., 2003). Recurrent networks added context memory. Transformers added attention between tokens. BERT and GPT used broad pre-training in 2018. GPT-3 demonstrated few-example prompting in 2020. Instruction and preference training then helped create assistant behaviour.

## 2. From transformer to LLM: data, scale and context

A **parameter** is one learned number. A training **token** is one piece processed from the dataset. **Compute** counts the operations used to learn from those pieces. Keep these quantities separate: increasing the number of tokens is different from increasing the number of model parameters.

### The pipeline

1. **Collect** web crawls (e.g. Common Crawl), books, code, maths, papers and multilingual text.
2. **Clean and filter:** remove repeated copies (duplicates can increase memorisation), remove low-quality and unsafe text (often with classifiers), remove benchmark test sets (decontamination), balance the mix. Synthetic data generated by other models is increasingly used.
3. **Tokenise** with a trained BPE-style tokenizer.
4. **Pre-train** with next-token prediction on thousands of GPUs for weeks.
5. **Post-train** into an assistant (week 8).

The architecture is last week's decoder transformer, scaled up.

### Compute

$$C \approx 6\,N\,D$$

**Small planning example.** One billion parameters trained on twenty billion tokens gives approximately 6 × 10⁹ × 2 × 10¹⁰ = 1.2 × 10²⁰ operations. The larger worked example below uses the same multiplication.

**FLOPs** counts floating-point numerical operations. For a dense transformer, C ≈ 6ND is a rough estimate: about two operations per parameter-token for the forward pass and four for backward computation. It omits some architecture and system costs.

With $N = 7\times10^9$ parameters and $D = 2\times10^{12}$ tokens, $C \approx 8.4\times10^{22}$ operations. At $4\times10^{14}$ operations per second per GPU, divide to get $2.1\times10^8$ GPU-seconds, or about 58,000 GPU-hours. Actual time depends on utilisation and coordination. Many teams therefore adapt pretrained models.

### Data scale

GPT-3 was trained on ≈ 300 B tokens (2020), Chinchilla on 1.4 T (2022), Llama 3 on more than 15 T (2024); Hugging Face's open FineWeb dataset contains ≈ 15 T filtered web tokens. One trillion tokens ≈ 750 billion English words.

### Scaling laws

Kaplan et al. (2020) and Hoffmann et al. (2022) found that pre-training loss follows smooth power laws in parameters and data. The Chinchilla fit is

$$L(N, D) = E + \frac{A}{N^{\alpha}} + \frac{B}{D^{\beta}}, \quad E \approx 1.69,\; A \approx 406.4,\; B \approx 410.7,\; \alpha \approx 0.34,\; \beta \approx 0.28$$

**Read the scaling fit.** E is the fitted baseline loss. The next term decreases with model size N, and the last decreases with data D. Doubling N multiplies its term by 2⁻⁰·³⁴, about 0.79, while keeping D fixed. These constants describe the study’s fit.

For the Chinchilla study’s setup, about **20 training tokens per parameter** gave a useful balance under a fixed compute budget. GPT-3 used about 1.7 tokens per parameter and was under-trained by that criterion.

The ratio is a study result, not a rule for all tasks. Llama 3 8B used roughly 1900 tokens per parameter. More training for a smaller model can be worthwhile when many later requests make inference cost important.

![Scaling laws](fig:scaling)

### In-context learning and emergence

**In-context learning** means a model follows examples in the prompt while its weights stay fixed. For example, show “good: positive” and “awful: negative”, then ask for the label of “great”.

Some abilities appear abruptly as model size grows. Schaeffer et al. (2023) show that scoring rules such as exact match can make gradual improvements look sudden. Test the ability your task needs.

### Context windows

The **context window** is a token limit for the model request. Depending on the system, instructions, history, retrieved documents, tool results and the answer share this budget. Check model-specific limits and output caps.

Longer input can cost more and take longer. Information in the middle may be used less reliably, as studied by Liu et al. (2023). A large limit does not remove the need to choose relevant material. Retrieval in week 12 makes that selection explicit.

## 3. Decoding strategies

| Strategy | Mechanism | Use for | Risk |
|---|---|---|---|
| Greedy | Most likely token each step | Short factual answers, extraction | Loops, bland text |
| Beam search | Keep k best partial sequences | Translation, summarisation with encoder–decoders | Generic output in open chat |
| Temperature | Divide logits by T before softmax | Controlling creativity | High T: errors |
| Top-k | Sample among k most likely tokens | Removing the unlikely tail | Ignores model confidence |
| Top-p (nucleus) | Sample among the smallest set with cumulative probability ≥ p | General chat/writing | Interacts with temperature |
| Repetition penalty | Down-weight used tokens | Long generation | Can corrupt names, numbers, code |

**Worked example (top-p).** Logits [2, 1, 0.5, 0.1, −1] give probabilities [0.56, 0.21, 0.12, 0.08, 0.03]. With $p = 0.8$ the cumulative sums are 0.56, 0.76, 0.89: the nucleus is the first three tokens; the rest are removed and the three kept probabilities are renormalised.

## 4. LLM families

### By architecture

* **Encoder-only:** BERT (2018), RoBERTa, DeBERTa, ModernBERT (2024), most embedding models. Masked-language-model pre-training; bidirectional. Use: classification, tagging, embeddings for search. Not a free-text generator.
* **Encoder–decoder:** T5 (2019; Flan-T5 is instruction-tuned), BART and mT5 transform input text into generated output text. Whisper encodes audio and decodes transcript text; its input is audio, not text.
* **Decoder-style text generation families:** GPT family (OpenAI), Claude (Anthropic), Gemini (Google), Llama (Meta), Gemma (Google, open-weight), Qwen (Alibaba), DeepSeek, Mistral, Phi (Microsoft), OLMo (Ai2, fully open with data and code), gpt-oss (OpenAI open-weight, 2025).

### Newer categories

* **Small language models** (≈ 0.1–8 B parameters): run locally or on devices; with good data and distillation they match much larger older models on many tasks.
* **Mixture-of-experts:** many parameters, few active per token (week 5); need memory for all experts.
* **Reasoning models:** trained (usually with reinforcement learning on checkable problems) to produce a long chain of reasoning before answering; spend **test-time compute**. Examples: OpenAI's o-series (2024), DeepSeek-R1 (2025, open), thinking modes in Claude, Gemini and Qwen3. Visible reasoning text is not guaranteed to reflect the internal computation.
* **Multimodal LLMs:** weeks 9–10.

## 5. Choosing and using models

### Model cards

A **model card** describes intended uses, known limits and evaluation. Read the stated training sources, languages and dates. Check how tests ran and whether the licence allows your use.

Technical details include size, memory needs, tokenizer, context limit and chat template. A **chat template** formats message roles and boundaries for that model. Missing information matters when assessing fit for your application (Mitchell et al., 2019).

### Licences

| Type | Examples | Usually means |
|---|---|---|
| Permissive (Apache 2.0, MIT) | Qwen (most), OLMo, Phi, DeepSeek-R1, gpt-oss | Use, modify and commercialise with notices |
| Community/custom | Llama, Gemma | Free use with acceptable-use policies and conditions (Llama: separate licence above 700 M monthly users) |
| OpenRAIL | Stable Diffusion 1.5, BLOOM | Open use with listed prohibited uses |
| Non-commercial research | Releases explicitly restricted to research | Check the exact licence and revision |
| Proprietary API terms | GPT, Claude, Gemini | Pay per use; provider sets data and output terms |

### Benchmarks

| Benchmark | Measures | Caveat |
|---|---|---|
| MMLU / MMLU-Pro | Multiple-choice knowledge | Saturation, contamination |
| GSM8K, MATH | Maths problems | Format sensitivity, memorisation |
| HumanEval, SWE-bench | Code generation; real repository fixes | Narrow languages and tasks |
| GPQA | Hard graduate-level science | Small |
| Human preference arenas | Pairwise votes (Elo) | Style and length bias |

Build a small test set from your own task (week 7) and evaluate shortlisted models with fixed prompts and settings.

### API vs local

An **API** is a software connection for sending a request and receiving a result. With a hosted model, the provider runs the hardware. Check data handling, token costs, request limits and model-version changes.

With a local or self-hosted model, you manage memory, hardware, updates and safety checks. You can control input data location and model versions. Transformers, Ollama and vLLM support these workflows. Many servers accept role/content chat messages, but supported features differ.

```python
from transformers import pipeline
chat = pipeline("text-generation", model="Qwen/Qwen2.5-0.5B-Instruct")
out = chat([{"role": "user", "content": "Explain tokens in one sentence."}],
           max_new_tokens=60, do_sample=False)
print(out[0]["generated_text"][-1]["content"])
```

### A selection process

Define the task → list constraints (privacy, budget, latency, hardware, licence, languages) → shortlist 2–4 candidates → evaluate on your own test set (quality, cost, latency) → decide, document and re-test when models change. Choose a model that meets the measured quality requirement within privacy, licence, time and cost constraints.

# Common misconceptions

| Misconception | Correction |
|---|---|
| "BERT, T5 and GPT are interchangeable chatbots." | Encoder, encoder–decoder and decoder models do different jobs. |
| "Bigger is always better." | Task fit, data, post-training, cost and latency matter; small models often suffice. |
| "Open-weight means open-source and free to use for anything." | Weights ≠ data/code; licences impose conditions. |
| "A top leaderboard score means the model is best for my task." | Benchmarks can be contaminated or saturated; test on your own data. |
| "A million-token context means retrieval is unnecessary." | Cost, latency and lost-in-the-middle effects remain. |
| "Reasoning models show their true reasoning." | Visible reasoning may not be faithful; check answers. |
| "Temperature 0 makes an API perfectly reproducible." | Server-side changes and non-determinism can still alter outputs. |

# Responsible AI lens: large language models

* **Data source history (provenance) and copyright:** limited disclosure of training data; ongoing litigation.
* **Bias:** stereotyped outputs (e.g. BERT's gendered predictions in the lab) and unequal quality across languages and dialects.
* **Hallucination and overconfidence:** fluent answers without guarantees.
* **Privacy:** memorisation of training data; data sent to APIs.
* **Openness:** open weights support scrutiny and local control but also misuse; the EU AI Act adds obligations for general-purpose AI model providers.

# Glossary

| Term | Meaning |
|---|---|
| n-gram model | Predicts the next word from the previous n − 1 words by counting |
| Word embedding | Dense learned vector per word |

# Detailed explanations behind the short slides

These explanations retain the detail moved off crowded slides. Read the short slide first, then use this reference for deeper discussion.

## Slide 7: Where it started: n-gram language models

- An n-gram uses n − 1 previous words to predict the next word from counts.

- Example: after “the cat”, a trigram model counts how often each next word appears.

- Long phrases often have no examples: sparsity. Smoothing helps with zero counts. Embeddings share information between similar words.

## Slide 8: Each generation fixed a limitation of the last

| Approach | Representation | Context | Main limitation |
|---|---|---|---|
| n-gram LM | Word identities and counts | Previous n − 1 words | Many phrases have no counts. Similar words share no information. |
| Word embeddings | One learned vector per word | Fixed vector when used alone | "Bank" keeps the same vector for river and money meanings. |
| RNN / LSTM | A memory vector updated at each word | Earlier words through the memory state | Reading is sequential. Distant information can fade. |
| Transformer LLM | Vectors updated by attention | Tokens inside its context limit | Long inputs cost more. Plausible answers can be false. |

## Slide 10: The LLM pipeline, in more detail

- Data quality, languages and task mix affect what the model learns.

- A large language model uses the transformer ideas from week 5 at larger data and compute scales.

- Collect data: Authorised examples from text, code and other sources

- Clean & filter: Remove poor examples, duplicates and test-set overlap

- Tokenise: Split text into vocabulary pieces and token IDs

- Pre-train: Learn to predict the next token across many examples

- Post-train: Learn from instructions and feedback about answer quality

## Slide 11: How much compute does pre-training need?

- A rough dense-transformer estimate is C ≈ 6 × parameters × training tokens. FLOPs count numerical operations.

- For 7 billion parameters and 2 trillion tokens, C ≈ 8.4 × 10²² operations.

- At 400 trillion operations per second per GPU, this is about 58,000 GPU-hours. Hardware and utilisation affect real cost.

## Slide 12: Scaling laws: loss is predictable from size and data

- **Scaling laws** describe how average training loss often changes with model size and data amount.

- The Chinchilla study suggested about 20 training tokens per parameter for its fixed-compute setup.

- This is a planning guide, not a universal rule. Data, architecture and deployment costs affect the best choice.

- Some later small models use much more training data so they can be cheaper to run.

## Slide 14: In-context learning and 'emergent' abilities

- **In-context learning** means following a task shown by examples in the prompt. The weights stay fixed.

- Example: “good: positive, awful: negative, great: ?”.

- Some measured abilities appear suddenly as size grows. Different scoring rules can make gradual progress look sudden.

- Test the ability your task needs on realistic examples.

## Slide 15: Context windows: how much the model can see at once

- A **context window** limits how many tokens a request can include.

- It may include instructions, conversation, retrieved text, tool results and generated output.

- A larger advertised limit does not guarantee equal use of every position. Important details can be missed in the middle.

- Selecting useful documents still matters, even with long context (week 12).

## Slide 16: Tokenisers differ between model families

- The figure counts tokens for the same texts under five tokenizers.

- A tokenizer's vocabulary affects how it splits languages and code.

- Compare actual pieces and counts: they affect cost, speed and how much text fits.

## Slide 18: Decoding strategies compared

| Strategy | How it works | Good for | Watch out for |
|---|---|---|---|
| Greedy | Choose the highest-probability token | Repeatable selection for extraction | Can repeat itself. Check output correctness. |
| Beam search | Keep several high-scoring partial sequences | Translation or constrained sequence tasks | Can favour generic or short outputs. |
| Temperature | Divide scores by positive T, then sample | Adjust the spread of choices | Higher T adds variety and can add errors. |
| Top-k | Keep k highest-scoring candidates | Remove very unlikely choices | The same k may fit some steps poorly. |
| Top-p | Keep likely candidates until their total reaches p | Adapt candidate count to confidence | Check how it combines with temperature. |
| Repetition penalty | Reduce scores for previously used tokens | Reduce unwanted repetition | Can distort needed names, facts or code. |

## Slide 23: BERT vs. T5 vs. GPT-style: same input, different jobs

**BERT (encoder)**

- Fill a [MASK] using text on both sides

- Return candidate tokens or input vectors

- Useful for classification, entity tagging and embeddings

- Usually used to understand input

**T5 / Flan-T5 (enc–dec)**

- Read source text with the encoder

- Generate output with the decoder

- Useful for translation, summaries and question answering

- Flan versions also train on task instructions

**GPT-style (decoder)**

- Predict each next token from the existing context

- Generate continuations or chat replies

- Useful for writing, code and assistant tasks

- Chat behaviour depends on post-training and message format

## Slide 25: Newer categories that matter when choosing

- **Small language models:** Smaller models, often about 0.1–8 billion parameters, can suit narrow tasks. Check memory needs before running locally.

- **Mixture-of-experts:** A router activates a few expert networks per token. Total weight memory can still be large.

- **Reasoning models:** Use extra generated computation before the final answer. This can help some tasks but costs time and tokens.

- **Multimodal LLMs:** Process text with images, audio or video, depending on the model.

## Slide 31: Benchmarks: useful, but read them critically

| Benchmark | Measures | Caveat |
|---|---|---|
| MMLU / MMLU-Pro | Multiple-choice subject knowledge | Scores can hide test overlap or differences between versions. |
| GSM8K, MATH | Maths word problems | Answer format and memorised examples can affect scores. |
| HumanEval, SWE-bench | Code writing or repository fixes | Coverage of languages and task types is limited. |
| GPQA | Difficult graduate-level science questions | The set is small. Read the evaluation setup. |
| Human preference arenas | People compare pairs of answers | Length and writing style can influence votes. Your users may prefer differently. |

**Key idea:** Use benchmark scores to make a shortlist. Then compare models on examples from your actual task.

## Slide 35: What LLMs are used for, and where they struggle

- **Strong:** Try drafting, rewriting, summaries, translation, extraction or code help. Test quality for the task.

- **Strong with tools:** Use retrieved documents for sourced answers (week 12) or code tools for calculations.

## Slide 36: A practical process for choosing a model

**Key idea:** Choose a model that meets the measured quality requirement within your practical constraints.

- Define the task: Write example inputs and the output you need

- Constraints: Set data, cost, speed, hardware and licence requirements

- Shortlist: Choose 2–4 candidates that fit the requirements

- Evaluate on your data: Use the same test examples and settings to compare quality, cost and time

- Decide & monitor: Record the choice and test again when a model changes

## Slide 37: Responsible AI lens: large language models

- **Data rights**: check what is known about training sources and the model's licence.

- **Bias**: test the languages and groups your application serves.

- **Hallucination**: check important claims against reliable evidence.

- **Privacy**: models may repeat training data. Protect confidential input and check provider settings.

- **Accountability**: document versions, tests, limitations and who reviews errors.

## Slide 39: Summary

- Language models progressed from counts to learned vectors, recurrent memory and attention.

- LLM training needs suitable data and compute. C ≈ 6ND is a rough dense-model estimate.

- Scaling laws help planning. The best data-to-size ratio depends on the setup.

## Request-path and measurement checks

Local and hosted chat are alternative paths. Local code applies a template and slices the prefix from generated IDs. A chat API normally accepts messages and returns a separate answer; the provider handles its tokenisation. The current Hugging Face client supports `chat.completions.create`, but a provider must support the requested model. Check the model’s current availability and handle absent usage fields or request errors.

The reasoning experiment compares its full settings, not just the thinking switch: budgets and sampling parameters differ. A CPU quick run uses shorter budgets and fewer repeats. Its score is an execution demonstration, not directly comparable with the stored instructor experiment. Completion is checked conservatively against the actual budget and the closing thinking marker.

## Using pretrained models with Hugging Face pipelines
```python
from transformers import pipeline

fill = pipeline("fill-mask", model="bert-base-uncased")
fill("The capital of Ireland is [MASK].")

chat = pipeline("text-generation",
                model="Qwen/Qwen2.5-0.5B-Instruct")
messages = [{"role": "user",
             "content": "Explain tokens in one sentence."}]
out = chat(messages, max_new_tokens=60, do_sample=False)

```

## Querying a hosted model through an API
```python
import os
from huggingface_hub import InferenceClient

client = InferenceClient(api_key=os.environ["HF_TOKEN"])
resp = client.chat.completions.create(
    model="Qwen/Qwen2.5-7B-Instruct",
    messages=[{"role": "user",
               "content": "Name three LLM families."}],
    max_tokens=100, temperature=0.2)
print(resp.choices[0].message.content)
print(resp.usage)   # prompt and completion tokens
```
