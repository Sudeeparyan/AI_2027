# AI2027 Teaching Studio — operating guide

## What you now own

This is a portable Python command-line application plus the completed teaching pack. You own the source content, prompts, drawing code, notebook code, images, references and outputs. It does not depend on the conversation that created it. Extract the ZIP, keep the whole AI2027_Project folder and read this guide.

There are two connected loops:

1. **Content improvement:** sources → model-generated candidate → structural validation → optional model review → instructor edit/review → explicit apply.
2. **Artifact production:** accepted content → PowerPoint/Word/notebook → execution/layout checks → bounded layout repairs → saved images, previews and reports.

Existing materials can be rebuilt without any AI account. New AI-written revisions require a configured API provider, or an available local model with a compatible endpoint. The current writing is retained as editable JSON; the original conversation's internal reasoning is not a dependency or a reproducible API trace.

## How 12 weekly sets are produced

For each week the generator reads these files:

| Source file | Generated use |
|---|---|
| `lesson.json` | Weekly goals, teaching content and worked case in the Word guide |
| `slides.json` | Exact titles, slide explanations and speaker scripts, IDs s01–s40 |
| `visuals.json` | Block-diagram labels and diagram relationships |
| `study.json` | Extra explanation, exam practice, model answers and resources |
| `lab.ipynb` | Student notebook; shared tagged cells populated from content/shared |

`course.py --weeks all` loops through weeks 1–12. For each week it creates a classroom PPTX, editable PPTX, DOCX, IPYNB, PDF previews, exported images and a checks report. The requested minimum is **12 classroom decks + 12 Word guides + 12 notebooks = 36 main files**. Editable decks, PDFs, images and reports are additional files. Each deck currently has 40 slides.

The saved PNG on a slide is exported from its precise native diagram. `asset_manifest.json` records the matching asset. Python functions produce the native diagram; you can edit the diagram at its source without redrawing the entire deck. The conceptual illustration is a retained asset, with its generation prompt included. This application's text adapter does not automatically call an image-generation service.

## Install and rebuild without AI

Install Python 3.10+ and LibreOffice (`soffice` on PATH), then open a terminal in AI2027_Project:

```bash
python -m venv .venv
# macOS/Linux
source .venv/bin/activate
# Windows PowerShell instead: .venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python studio.py status
python course.py improve --weeks all --max-passes 3
```

Open `outputs/current/index.html` for the gallery. A week with unresolved automatic checks is not published to outputs/current. Each successful week is checkpointed immediately so a later failure does not discard its progress. Source hashes avoid unchanged rebuilds. Changing a renderer invalidates affected fingerprints conservatively. `--force` regenerates even unchanged inputs.

## Configure a model or account

Edit `config/providers.json`. Profiles contain no actual credentials. `key_env` is the **name of an environment variable**. `model_env` lets you select a model through the shell; otherwise `model` is used. Placeholder model names must be replaced with a model/deployment actually available to your account. Verify its supported token-limit parameter and context/output limits; provider compatibility does not mean every model supports identical parameters.

Included endpoint profiles: OpenAI, Google's compatibility endpoint, Azure OpenAI v1, NVIDIA hosted inference and a localhost compatible server. These are configuration templates. No live provider calls were made for this delivery because no API credentials were supplied. ChatGPT account/subscription limits and API project quotas are separate; signing into another ChatGPT account does not configure this app.

macOS/Linux (example with your available model):

```bash
export OPENAI_API_KEY='YOUR_API_KEY'
export OPENAI_MODEL='YOUR_AVAILABLE_MODEL_ID'
```

Windows PowerShell:

```powershell
$env:OPENAI_API_KEY = 'YOUR_API_KEY'
$env:OPENAI_MODEL = 'YOUR_AVAILABLE_MODEL_ID'
```

Use a secret manager or secure shell entry for real keys. `.env.example` documents variable names; this app does not automatically load .env files. Never paste keys into lesson JSON, a notebook, source documents or a prompt.

For an alternative institution project, duplicate a profile under a new name, e.g. `institution_backup`, and set its `key_env` to `INSTITUTION_BACKUP_KEY`. Configure only accounts/projects you are authorised to use. Changing credentials can be done by updating the environment variable; source files and completed work stay intact.

## Quota handling and model switching

To enable ordered fallback, change the routes, after configuring every listed profile:

```json
"routes": {
  "writer": ["openai_primary", "google_backup"],
  "reviewer": ["google_backup"]
}
```

The adapter retries temporary failures (408, 429 and selected 5xx errors), with bounded waits, then tries the next configured profile. It stops on missing credentials, authentication failures and invalid requests so configuration mistakes are visible. It stops when all profiles are unavailable. It does not bypass a provider's restrictions or create accounts.

When quota is exhausted:

1. Leave the run folder in place.
2. Set valid credentials/model for an authorised alternative profile, or wait for quota renewal.
3. Change the writer/reviewer route if needed.
4. Rerun the **same command and run name**. Completed matching content jobs are reused even if the provider changes. The original provider remains recorded for each completed job.

Use `--refresh` or a new `--run` name when you deliberately want completed content rewritten by the new model.

## Draft, review, apply and rebuild

First check the planned requests without making API calls:

```bash
python studio.py ingest
python studio.py draft --run iteration_03 --weeks 2 --artifacts all --dry-run
```

Then generate one week's slides first to check the selected model and output length:

```bash
python studio.py draft --run iteration_03 --weeks 2 --artifacts slides.json --max-jobs 1 --instruction "Explain the VAE latent sample using one worked icon example."
python studio.py review --run iteration_03 --weeks 2 --artifacts slides.json
```

Read the candidate and its `.review.json` file. Model review is advisory. After checking the candidate, apply it explicitly:

```bash
python studio.py apply --run iteration_03 --weeks 2 --artifacts slides.json
python course.py improve --weeks 2 --max-passes 3
```

`apply` checks that neither the canonical source nor the recorded candidate changed unexpectedly and saves backups before replacement. It does not execute candidate notebook code. Inspect generated code before the subsequent build, which executes notebooks for testing. Run untrusted code only in an appropriate isolated environment.

To make manual edits to a generated candidate, copy the reviewed changes into the canonical source yourself after making a backup. The apply command deliberately rejects candidates whose recorded hashes no longer match. Update related lesson, slide and study files together when changing a teaching claim.

For all 12 weeks and all five source types:

```bash
python studio.py draft --run iteration_04 --weeks all --artifacts all --max-jobs 12 --max-passes 2
# Repeat the same command until all 60 source-file jobs finish.
python studio.py review --run iteration_04 --weeks all --artifacts all --max-jobs 12
# Repeat review, inspect results and code, then apply selected weeks/files.
python studio.py apply --run iteration_04 --weeks 1 --artifacts all
python course.py improve --weeks 1 --max-passes 3
```

The 60 source-file jobs produce 36 main classroom files after rendering. Authoring each file separately improves resumability but requires a cross-file consistency review. Drafting does not silently publish or execute generated content.

## Cost, checkpoints and scaling

- `--max-jobs` limits new content jobs per invocation, not network attempts or currency spending.
- `--max-passes` limits structural correction attempts per job. One pass can try each configured profile with its configured retries. Worst-case request count is jobs × passes × profiles × (retries + 1).
- Response token limits are in each profile's `parameters`. Usage metadata records the accepted response; it is **not a complete billing ledger** for failed requests or rejected drafts. Set a spending limit with the provider.
- Checkpoints are per week, artifact and stage. Prompts and input changes invalidate matching work; changing accounts alone does not.
- A run lock prevents concurrent writes to the same authoring run. A crashed process can leave `.lock`; remove it only after confirming that process stopped.
- This release processes jobs sequentially, with file-backed checkpoints. It is a portable single-operator application, not a distributed job service.
- Separate draft runs may run on different machines. Synchronise accepted source revisions deliberately. Avoid concurrent apply/build commands against the same project folder.
- For larger deployments, the next implementation step is a database-backed job queue, shared object storage, transactional approval records and central secret management. These services are not included in this version.

## Sources and 2027 maintenance

All 11 supplied files are retained. `source_map.json` controls selected references per week. Authoring currently includes **up to the first 12,000 characters of each selected source**; checkpoint metadata records truncation. It is not semantic retrieval and does not claim to use every paragraph. Rework extraction/chunk selection if a relevant passage is beyond that limit. The beginner syllabus stays authoritative. Other module descriptors remain references; this package still represents one 12-week module.

The imported notes contain claims requiring checking: RAG does not guarantee truth; lower temperature does not universally guarantee deterministic output; headline failure percentages need traceable evidence; MCP standardises an interface but does not guarantee every integration works unchanged. Future-facing 2027 material must distinguish confirmed capabilities from proposed extensions. No uploaded claim is automatically treated as verified research.

Before each semester: check links, supported model IDs and API contracts; rerun notebooks; review slide screenshots; test a fresh student environment; retain the approved source version and final held-out questions separately.

## Restore, export and continue elsewhere

To restore a source, copy the corresponding file from `backups/<timestamp>/content/week_XX/` back to `content/week_XX/`, then rebuild. Build snapshots also record older accepted content. Use Git locally for additional reviewable history (`git init`, then commit accepted changes); do not commit secrets.

```bash
python -m unittest discover -s tests -v
python verify_release.py
python package_project.py
# Include all earlier build outputs if desired:
python package_project.py --include-history
```

The exporter includes current outputs, sources and generators; excludes virtual environments, drafts, backups, .env files and private config files; and replaces the active provider config with the clean example. Keep personal drafts/backups separately if needed. Check any newly added files for sensitive information before sharing.

In a new AI session, provide the ZIP and `docs/HANDOFF.md`. The recipient can inspect the source and resume work without the old chat history.

## Revise the full lesson architecture

The current lesson has 40 slides: an opening case and vote, four six-slide concept cycles, and thirteen application/revision slides. Each concept cycle moves from a prediction through a familiar analogy, explicit mapping and limitation, actual mechanism, worked example and answer reveal. The authored data lives in `content/teaching_design/author_lessons.py`; run it, then `build_lessons.py` to replace the 12 canonical `slides.json` files. For small revisions, edit `slides.json` directly and rebuild only that week. The production build never silently recompiles the authored data. The Word guide and notebook introduction read the same weekly design data.
